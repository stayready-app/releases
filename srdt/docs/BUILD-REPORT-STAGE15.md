## Реальные отдельные процессы, UDP loopback

[Полные JSON-результаты](stage15-process-tests.json). Сервер и нагрузочный клиент — разные
процессы; RSS/CPU ниже относятся только к серверу. Каждый ответ проверялся побайтово.

| Сценарий | Результат | Время генератора, с | Наблюдавшийся max RSS сервера, МиБ | CPU сервера, с | Пиковый резерв Budget, КиБ | ResourceDrops |
|---|---|---:|---:|---:|---:|---:|
| 32 клиента, без заданных нарушений | PASS | 0.555 | 6.55 | 0.04 | 528.0 | 12 |
| 32 клиента, фильтр 800–1100 в обе стороны | PASS | 1.042 | 6.90 | 0.10 | 946.0 | 0 |
| 1000 соединений, проверка + простой 1 с | PASS | 1.347 | 9.11 | 0.16 | 0.1 | 0 |
| 200 клиентов, 100 МиБ + эхо | PASS | 5.163 | 34.15 | 5.07 | 16896.0 | 186622 |
| 1 сессия, 100 МиБ + эхо | PASS | 2.079 | 9.42 | 1.77 | 88.0 | 0 |

100 МиБ = 104857600 исходных байт плюс 104857600 байт эха. Это не тест только одного
направления. После корректной остановки всех пяти серверов active_sessions=0, buffer_bytes=0.
Освобождение резервов не означает мгновенный возврат всех страниц RSS операционной системе.

Условия: GOMAXPROCS=2, GOMEMLIMIT=128MiB; max-per-ip=1024, hello-rate=10000,
hello-burst=2048, idle-timeout=180s, progress-timeout=90s. Иначе localhost-нагрузка превысила
бы admission defaults. RSS снимался каждые 20 мс — возможны непросэмплированные пики.
CPU — user+system time из /proc, с разрешением системного тика, без формального профилирования.
2 Go execution slot не имитируют слабый физический процессор. GOMEMLIMIT мягкий, не предел RSS [1].
На реальном узле 2 ГБ одновременно с Xray и агентами эти испытания не выполнены.

## Сопоставимый повтор Stage 14 → Stage 15

Сначала отдельно собран неизменённый Stage 14, затем последовательно (не одновременно)
выполнен тот же bulk-сценарий. В обоих случаях 200 клиентов, 6400 сообщений × 16 КиБ,
100 МиБ + эхо, точная проверка всех ответов. Это один парный запуск, не доверительный интервал.

| Показатель | Stage 14, повтор в этой среде | Stage 15 |
|---|---:|---:|
| Время генератора, с | 8.219 | 5.163 |
| CPU серверного процесса, с | 8.16 | 5.07 |
| Наблюдавшийся max RSS, МиБ | 37.74 | 34.15 |
| ResourceDrops | 375017 | 186622 |
| Входящих датаграмм | 910541 | 676797 |
| Исходящих датаграмм | 759538 | 612095 |

CPU уменьшился на 37.9%,
время — на 37.2%,
RSS — на 9.5%.
ResourceDrops сократились, но остались: нет negotiated receive credits/полного flow control.
Поэтому этот результат — улучшение прототипа, не достигнутый production SLA.

Исходный baseline JSON: [stage15-before-bulk.json](stage15-before-bulk.json).
Пиковый Budget после изменений стал выше, потому что он теперь резервирует и метаданные
повторов. Сравнивать эти счётчики как одинаковую меру фактической памяти нельзя.

## Микротесты горячего пути

Те же три benchmark-функции запускались на исходном и исправленном коде, по три повторения.
Median ns/op ниже; объём B/op относится к тестовой операции, не ко всему серверному пакету.

| Операция | Stage 14, ns/op (median) | Stage 15, ns/op (median) | Выделения Stage 14 → 15 |
|---|---:|---:|---|
| ACK уже полностью подтверждённого 32-КиБ сообщения | 44127 | 3.591 | 0 → 0 |
| Повтор принятого фрагмента 900 байт | 1500 | 172.9 | 52 B / 2 alloc → 52 B / 2 alloc |
| Поиск/упаковка retry при частичных ACK | 427.1 | 24.31 | 1536 B / 1 alloc → 0 B / 0 alloc |

Первый результат отражает специальный O(1) terminal-state shortcut, не универсальное
ускорение любого ACK на тысячи раз. Напечатанные самим benchmark MB/s здесь не являются
сетевой скоростью; их не следует использовать. Нулевые аллокации retry не означают zero-allocation
во всём протоколе. Остались аллокации ACK/служебных объектов, описанные в source/coverage.
Журналы: [до](stage15-bench-before.txt), [после](stage15-bench-after.txt).
