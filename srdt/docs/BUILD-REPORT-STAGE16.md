# Stage 16 — сборка, тесты, память, производительность

Дата: 2026-11-01. Основа: полный архив Stage 15. **Лабораторный прототип, не production.**
В этом отчёте приведены реально выполненные команды и измерения последней версии исходников.
Другие stage16-initial-* журналы — промежуточные прогоны, не финальные показатели.

## Среда и воспроизведение

* Go: `go1.23.2 linux/amd64`, Python 3.13.5, Linux x86_64.
* Клиент и сервер сетевых unit-тестов работают через реальные UDP-сокеты Linux loopback.
* Нагрузочные server/load — **разные процессы**. Таблица RSS/CPU измеряет только сервер.
* Для server: `GOMAXPROCS=2`, `GOMEMLIMIT=128MiB`. Это не CPU affinity/cgroup и не имитация
  слабой VPS. GOMEMLIMIT — мягкое ограничение Go runtime, не жёсткий потолок RSS [3].
* RSS и CPU считываются из /proc каждые 20 мс; краткие пики между выборками могут не попасть.
  Контейнер общий, выделенные CPU не обеспечены. Три повтора — не статистическое доказательство.

```bash
bash scripts/verify.sh
python3 scripts/integration.py --bulk
python3 scripts/compare.py --baseline /path/to/srdt-stage15 --runs 3
python3 scripts/cli_smoke.py --baseline /path/to/srdt-stage15
```

Для сравнения baseline заново собран из неизменённых Go-исходников Stage 15 с тем же Go.
В него добавлен только одинаковый WAN-delay `_test.go` — не код библиотеки/приложения.
Скрипты требуют Python 3 и Linux /proc; архив содержит исходники скриптов и все результаты.

## Парное сравнение Stage 15 / Stage 16

Три чередующихся запуска каждой версии: 200 клиентов, 100 МиБ суммарно и 100 МиБ эха.
Одинаковые серверные лимиты, toolchain и workload. Оба клиента используют реализацию своего
этапа; у Stage 16 добавлена admission-схема и независимое пополнение ограниченных слотов.

| Показатель, медиана трёх запусков | Stage 15 | Stage 16 |
|---|---:|---:|
| Время нагрузки, с | 4.985 | 4.209 |
| CPU серверного процесса, с | 4.89 | 4.18 |
| Наблюдавшийся максимум RSS, МиБ | 33.73 | 34.75 |
| ResourceDrops, медиана | 184,406 | 0 |
| Проверка данных во всех запусках | PASS | PASS |

Фактические ResourceDrops Stage 15: [184406, 186966, 177715]; Stage 16: [0, 0, 0].
В этом наборе медиана CPU снизилась примерно на 14.5%, времени —
на 15.6%. **RSS не уменьшился**: медиана выросла примерно
на 1.03 МиБ. Следовательно, эффект этапа — не общее
снижение памяти, а согласованное резервирование и устранение отказов по ёмкости при передаче.
Потери в сети/сокетах и повторы не исчезли; нулевой ResourceDrops означает только отсутствие
отказов принять DATA из-за локальных лимитов.

Сырые данные всех запусков: [stage16-comparison/summary.json](stage16-comparison/summary.json),
соседние `*-bulk-N.json/log`. Ранний одиночный замер показывал более низкий RSS, но он
не используется вместо последней серии. Нельзя выбирать лучший прогон и выдавать его за норму.

## Существенная регрессия на RTT — не скрыта

Один клиент, 32 сообщения по 4096 байт (128 КиБ + эхо), реальный промежуточный UDP relay
добавляет **40 мс в каждом направлении**, без намеренной потери. Это RTT примерно 80 мс,
а не реальная внешняя WAN. Время включает тот же финальный 300-мс период обработки хвостовых ACK.

| Время обмена | Stage 15 | Stage 16 |
|---|---:|---:|
| Три запуска, мс | [1044, 1043, 1042] | [2319, 2330, 2322] |
| Медиана, мс | 1043 | 2322 |

**Stage 16 медленнее примерно в 2.23 раза** в этом маленьком WAN-delay сценарии.
Основная новая причина — отдельный OPEN/GRANT перед каждым сообщением в обе стороны.
Фиксированный RTO=80 мс дополнительно даёт лишние повторы около RTT; в журналах видны
поздние/повторные пакеты и ACK, счётчик InvalidPackets не означает исключительно атаки.

Это сознательно отмеченный недостаток текущей message-admission реализации, не приемлемый
финальный результат по производительности. Прежде production нужно уменьшить обязательные
обмены, например ограниченными пакетными/накопительными кредитами и pipelining, сохраняя
реальную обеспеченность каждого разрешения памятью. Затем/совместно нужны адаптивный RTO,
pacing и congestion control. Receive flow control не заменяет управление перегрузкой пути [1,2].

Логи: [stage15-wan.txt](stage16-comparison/stage15-wan.txt),
[stage16-wan.txt](stage16-comparison/stage16-wan.txt).

## История проверок и пределы результата

Первый запуск comparison завершился после bulk, до WAN: защита скрипта обнаружила отличие
baseline test fixture только в gofmt-форматировании. После форматирования был выполнен полный
повторный запуск. Первая CLI-проверка прошла modern/filter и прервалась перед legacy:
извлечённый старый client binary не имел execute bit. Клиент Stage 15 пересобран из исходников,
все пять CLI-сценариев затем пройдены. Оба первоначальных журнала сохранены (`*-first-attempt.txt`).
Это не скрытые падения протокола, но первые неполные запуски не считаются успешными.

Длительная реальная работа на слабой VPS с 2 ГБ вместе с Xray/sing-box, Windows runtime,
WAN, перегрузка канала, независимый криптоаудит и актуальный security scan не выполнены.
Flow-control механизм прошёл перечисленные проверки, но проект в целом не готов к эксплуатации.

## Упаковка
