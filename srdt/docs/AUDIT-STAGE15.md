# Аудит качества и исправления — Stage 15

Дата: 2026-11-01. Исходная точка: полный архив Stage 14. Проверены исходники secureudp,
reliable, netreliable, emulator, testkit, CLI, схемы владения памятью и скрипты проверок.
Это инженерная ревизия с воспроизведением ошибок, а не независимый криптографический аудит.

## Вердикт

В Stage 14 обнаружены реальные нарушения корректности, риски повторного nonce, неучтённый
рост метаданных и дорогие операции на горячем пути. Исправлены перечисленные ниже случаи.
Архив Stage 15 проходит сборку, весь race suite, регрессии, короткий fuzz и реальные UDP-тесты.
Однако жёсткие production-требования ещё не закрыты: flow control, congestion control,
адаптивные таймауты, проверенная криптография и актуальный toolchain остаются обязательными.

## Контракты, которые изменились или уточнены

**Общий Budget.** BufferCharge(N) = N + bitmap + 64 × rangeLimit(N), где
rangeLimit(N) = min(N, 1024, max(8, ceil(N/256))). Резерв включает ещё не выделенные
дескрипторы будущей отправки. Например, 32 КиБ payload резервируют 44 КиБ, не 36 КиБ.
Входящая и исходящая половины делят один резерв без копирования payload/bitmap.
Старые счётчики PeakBufferBytes нельзя напрямую сравнивать как фактическую heap-память:
теперь счётчик учитывает больше категорий. Аллокатор и transient overlap остаются вне счётчика.

**Replay.** Identity имеет ограниченный реестр на весь срок ключа, Server — собственный
меньший admission registry. Это исправляет повторное создание сессии внутри одного процесса,
но не позволяет безопасно переносить старый private key в новый объект без реестра.
На заполнении происходит отказ новых соединений, а не потенциально опасное вытеснение ID.

**Доставка.** Дедупликация не подразумевает неограниченный журнал всех ID. После retirement
неизвестный старый ID не принимается. Эхо-слой использует последовательные нечётные request ID,
чётные ответы и окно опережения. Для общего production API нужно явно закрепить доставку,
flow-control credits и ошибки просроченных сообщений. Никакой гарантии после падения процесса нет.

**Concurrency.** Session/Queue/Receiver одновладельческие. Mutex Identity защищает admission,
mutex сервера — согласованные Stats; сам event loop один. Send callback должен завершить
использование slice до возврата. Эмулятор также имеет одного владельца. Лимиты событий и
дескрипторов ограничивают асимптотику, а не делают runtime/GC безаллокационными.

**Совместимость.** DATA/ACK формат не менялся, прежние CLI options сохранены. Поведение
ошибочных входов стало строже. Raw echo по-прежнему одно ненадёжное сообщение; --reliable,
--batch и --multi используют общий reliable server. Максимум UDP envelope всё ещё 1200 байт.

## Дополнительные проверки устойчивости

Новый test-only relay использует отдельный реальный UDP-сокет между клиентом и сервером.
Он повреждает/отбрасывает уже сформированные зашифрованные пакеты в обоих направлениях,
а не подменяет результат Send непосредственно в отправителе. Проверены:

* 5% потерь, 5% повторов, 2% повреждений, задержки 1–15 мс и вставки невалидных копий;
* фильтр размеров 800–1100 байт, 2% потерь, 3% повторов, 0–8 мс задержки и вставки;
* потеря первого WELCOME; временная блокировка ACK 350 мс;
* задержка 40–100 мс в каждом направлении, 1% потерь и вставки (модель RTT ~80–200 мс);
* постоянная блокировка: ограниченный timeout, не ложный успех;
* 1024 аутентифицированных начатых сборки при глобальном бюджете только на 4 сообщения:
  остальные отвергаются, после expiry освобождаются буферы/очереди/heap.

В каждом успешном relay-сценарии проверяется 128 КиБ и точные байты каждого сообщения.
Результаты: [stage15-fault-tests.txt](stage15-fault-tests.txt). Runtime scheduling не фиксируется
одним seed; это не идеальная детерминированная симуляция и не реальная внешняя WAN.

## Измерения и оставшиеся приоритеты

Числа и команды — в [BUILD-REPORT.md](BUILD-REPORT.md). Низкий RSS не означает готовность
обслуживать произвольное число активных клиентов. В повторном bulk-тесте осталось 186622
resource drops. Это отказы admission для новых фрагментов при занятости очередей, не ошибки
проверки содержимого, но они создают лишний CPU/трафик. Их нельзя объявлять решёнными.

Порядок дальнейшего исправления архитектуры:

1. Согласованные receive credits и backpressure: не посылать то, что получатель не может удержать;
   справедливое распределение ресурсов между сессиями, не только общий лимит.
2. RTT/loss detection, адаптивный RTO, pacing и path congestion control. Подтверждения диапазонов
   передачи/логических байтов должны иметь чёткую семантику; не приравнивать каждую потерю к DPI.
3. Проверенная схема session keys/epoch/rotation, индивидуальная авторизация и защита admission.
4. Потоковый API с bounded client buffers, soak test, поддерживаемый Go, настоящий Windows/Ubuntu
   и слабый сервер с Xray; затем интеграция/дополнительные carriers/маскировка.

Полный перечень ограничений — [SECURITY.md](SECURITY.md). Ничего из этих пунктов не считается
выполненным только на основании нынешних коротких тестов.
