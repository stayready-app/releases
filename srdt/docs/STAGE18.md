# Stage 18 — ограничение темпа DATA и экспериментальное окно перегрузки

Основа: полный исходный архив Stage 17, контрольная сумма в `stage18-provenance.json`.
Это лабораторный message/UDP echo-стенд, не готовый VPN и не реализация QUIC.
Требования сервера остаются прежними: 2 ГБ общей RAM, слабый CPU, множество клиентов,
часть ресурсов занята Xray и другими службами. Цель этапа — уменьшить выбросы DATA
и стоимость повторов, не ослабляя жёсткое резервирование приёма.

## 1. Два независимых ограничения

**Приёмное окно** (Stage 17) — реальные резервы payload/bitmap/metadata у получателя.
Получение WINDOW_GRANT не означает, что сеть способна пропустить все эти данные сразу.

**Окно перегрузки** (Stage 18) — дополнительный локальный лимит новых неподтверждённых
логических байтов. Новые DATA ограничены минимумом настроенного `maxInFlight`,
этого окна и уже предоставленных разрешений. Повторы не становятся новыми логическими
байтами; их скорость отдельно ограничивается pacer.

Контроллер включён по умолчанию у `netreliable` клиента и сервера, в том числе в старых
reliable wrapper API. В чистой библиотеке `reliable.Queue` требуется явный вызов
`EnableCongestionControl(maxPayload, wireOverhead)` **до Enqueue**. Это сохраняет
совместимость старых виртуальных тестов и возможность надёжных stream-carriers без
дублирования механизмов нижнего транспорта.

Формат сообщений и криптография не менялись. Stage 18 и Stage 17 могут общаться без
новых флагов. Старый Stage 16 требует прежнего `--legacy-credits` клиента.
Ни один старый CLI-параметр не удалён. Новый `--no-congestion` — только для лабораторного
сравнения и отключает управление в собственном отправляющем направлении. Для A/B обе
стороны запускаются с ним; это не рекомендуемый профиль эксплуатации.

## 2. Точная политика контроллера

При MSS=900 байт payload:

* начальное окно `min(10*MSS, maxInFlight)`;
* минимальное окно `min(2*MSS, maxInFlight)`;
* верхняя граница — настроенное ограничение `maxInFlight`;
* до порога: увеличение по новым уникально подтверждённым байтам;
* после порога: приблизительно один MSS на окно вновь подтверждённых байтов;
* увеличение подавлено, когда полёт меньше половины окна или ACK относится к старому/
  повторно переданному диапазону;
* при таймауте: порог уменьшается вдвое, окно сбрасывается до минимального;
* несколько истекших диапазонов одного старого полёта — одно событие уменьшения;
* отдельный позже потерянный повтор может начать следующую эпоху потерь.

Неверный ACK не меняет окно. Повторный ACK не даёт повторного прироста. После уменьшения
окна уже переданные данные не отзываются: новых байтов не добавляется, но повторы
разрешены через pacer, поэтому полное окно не вызывает взаимной блокировки.

Таймауты по-прежнему используют оценку RTT/RTO Stage 17, Karn-подобное исключение
неоднозначных измерений и backoff. Быстрой классификации потери по номерам пакетов нет.

## 3. Pacer и планировщик

Используется ограниченный token bucket. Начальный запас — стоимость двух полных DATA.
На медленном пути максимальный запас — четыре DATA. На быстром пути он расширяется
только до одного кванта отправки (1 мс), не более окна перегрузки и не более 64 полных
DATA; нижняя граница ёмкости остаётся четыре DATA, чтобы небольшое настроенное окно
не вызывало голодания. Формула: `max(4*unit, min(wireWindow, rate*1ms, 64*unit))`.
Стоимость **каждой** передачи, включая повтор и локально неудавшийся UDP send,
равна `payload + wireOverhead`.

В `netreliable` overhead = 106 байт: 25 заголовок сессии, 16 AEAD, 17 фрейм, 8 UDP,
40 IPv6 без extension headers. Для IPv4 без опций это консервативная оценка. L2,
внешние туннели и будущий padding DATA сюда не входят. При изменении wire формата эту
величину необходимо пересматривать.

Темп = `cwnd / RTT`, пересчитанный в оценку внешних байтов через MSS/overhead.
До первого измерения используется 100 мс, нижняя граница RTT для темпа — 100 мкс.
Нет множителя ускорения выше cwnd/RTT. Это сознательно консервативный профиль.
Пауза не накапливает неограниченную пачку; после простоя не сохраняется прежнее большое
окно. Границы пачки заданы **в байтах**, не как жёсткое число маленьких датаграмм.
Маленьких пакетов в том же запасе может быть больше обозначенного числа полных DATA.
Сервер дополнительно сохраняет прежний лимит работы и количества фреймов за проход.

ACK и управление разрешениями не задерживаются DATA-pacer: они нужны для освобождения
ресурсов и восстановления. HELLO имеет прежний rate limit, credit probes — прежние
ограниченные таймеры. Это НЕ общий лимит всего исходящего трафика и не полная DoS-защита.

`Queue.Wake` учитывает следующий доступный момент pacing. Сервер по-прежнему использует
один цикл событий/UDP socket и одну запись в heap на сессию. При включённом контроллере
нет прежнего дополнительного 5-мс ожидания поверх готового pacer deadline. Чтение UDP
остаётся доступным даже при просроченной работе; бюджет обработки за проход сохранён.
На клиенте read deadline учитывает ближайшее полезное пробуждение с нижним шагом 1 мс
и верхним ожиданием 20 мс. Готовая входящая датаграмма немедленно разблокирует Read;
20 мс — не искусственная задержка каждого пакета. Это уменьшает холостой опрос
сокетов множества простаивающих/ожидающих клиентов; слишком частые пробуждения
самого генератора также конкурируют за CPU с сервером.

## 3a. Исправление зависания при фильтрации коротких DATA

Повторный прогон регрессий выявил постоянную недоставку хвоста. Когда исходный диапазон
короче `RetryFragment`, уменьшение только общего лимита повторов не меняет его длину.
Пример: сообщение 193 байта всегда даёт DATA UDP размером 251 байт; фильтр 200–280
отбрасывал и первую отправку, и все её повторы. Эта проблема касается общей библиотеки,
а ограничение congestion window сделало соответствующие короткие диапазоны вероятнее.

Теперь у каждого исходного диапазона есть один байт `packingRound`. По завершении полного
прохода повторов выбирается следующий из четырёх лимитов: исходная длина диапазона,
половина, четверть, восьмая часть (каждый дополнительно ограничен `retryPayload`, минимум
один байт). Затем цикл повторяется. RTO-backoff остаётся отдельным, не сбрасывается этим
циклом. Диапазоны/буферы не размножаются, размер `sentRange` по-прежнему укладывается
в прежний 64-байтовый резерв метаданных.

Проверка `TestCongestionTailSizeBlackhole` детерминированно падает до исправления и
проходит после него. Сохранены журналы обоих запусков и неудачного полного повторного
прогона. Формат на проводе не меняется: это другая упаковка тех же логических байтов.

Это ограниченная диверсификация повторов, не полноценное обучение профиля размеров.
Она не обещает обход произвольного множества запрещённых длин: если блокируются все
возможные упаковки или фиксированный ACK/HELLO, доставка остаётся невозможной. Слишком
мелкие повторы увеличивают overhead; pacing учитывает каждую их отправку.

## 3b. Исправление лавины мелких фрагментов при изменении окна

Первый процессный тест 1000 активных клиентов выявил серьёзную регрессию новой версии:
за 120 секунд успешно завершили обмен лишь 148 клиентов, сервер отправил более
10 миллионов датаграмм. RSS и резерв памяти оставались ограниченными, но нагрузка
на CPU и повторные передачи были неприемлемы. Неудачные результаты сохранены в
`docs/stage18-before-window-fix/` и не учитываются как успешная проверка выпуска.

Причина: даже один свободный байт в окне считался разрешением на новый DATA. При
уменьшении окна и мелких ACK создавались крошечные исходные диапазоны; их повторы
увеличивали число пакетов. `Wake` также считал такое остаточное окно поводом для
немедленного пробуждения, хотя полезной полной передачи ещё не было.

Теперь отправитель ждёт места под один выбранный полный фрагмент либо настоящий
хвост сообщения. Нижний необходимый объём дополнительно ограничен максимальным
размером самого окна, поэтому специально настроенное маленькое окно не блокируется.
Общая очередь и `Wake` используют один критерий. ACK и повторы старых данных продолжают
обрабатываться при заполнении окна; никаких дополнительных массивов для этого нет.

`TestCongestionNoTinyFreshFragmentFromWindowRemainder` воспроизводит случай окна
1801 байт: после двух фрагментов по 900 байт новый однобайтовый DATA не создаётся,
таймер не занят бессмысленным немедленным пробуждением. После освобождения окна
отправка полных фрагментов возобновляется. До исправления тест падает; оба журнала
сохранены. Процессный тест 1000 клиентов повторён отдельно и в финальном прогоне.
Это исправление не отменяет допустимые короткие сообщения/настоящие хвосты.

## 3c. Исправление ограничения пропускной способности частотой таймера

Отдельное сопоставление одной сессии на 100 МиБ выявило новую регрессию: 17,72 с
для промежуточного Stage 18 против 3,04 с Stage 17. Повторов и потерь в этом тесте
не было: задержку создавал сам ограничитель. Журналы сохранены в
`docs/stage18-before-pacer-quantum/stage18-single-comparison.json`.

Фиксированная пачка из четырёх DATA слишком мала для быстрого канала при реальной
гранулярности таймеров. Расчёт срока следующего пакета в десятках микросекунд не
гарантирует пробуждения через это время. Маленькое ведро фактически ограничивало
пропускную способность частотой пробуждений, независимо от доступности сети.

Теперь применяется ограниченная пачка одного кванта отправки, как описано выше.
На медленном пути прежний предел четырёх пакетов сохраняется, начальный burst остаётся
двухпакетным. Даже при очень маленькой оценке RTT или большой конфигурации окна
сохраняется абсолютный предел 64 полных DATA. После простоя используется прежний
restart: старый большой запас не переносится на возобновлённую отправку.

Добавлены тесты `TestCongestionPacerAmortizesFastPathTimerQuantum` и
`TestCongestionPacerSlowPathAndAbsoluteBurstCap`: полезная передача за квант на быстром
пути, прежняя граница медленного пути, абсолютный предел, отсутствие голодания при
минимальной конфигурации. Потребление состояния не увеличено; после изменения
повторяются полный verify, сравнение с Stage 17 и 1000-клиентский тест.

Это не обещание отсутствия накладных расходов контроллера. Остаточное замедление
на некоторых сценариях отдельно отражено в отчёте, а не скрыто за улучшением bulk.

## 4. Память и вычислительная сложность

Контроллер не хранит отдельную запись на каждый повтор/датаграмму, не создаёт таймеры,
goroutine и очереди payload. Состояние фиксированного размера, выделяется один раз на
отправляющее направление. Горячие операции token bucket выполняются за O(1).

Вместе с валидным ACK дополнительно проверяются пересекающиеся диапазоны сообщения;
число дескрипторов уже ограничено прежним бюджетом. Сами данные не копируются ради
ограничения темпа. Контроллер не входит в BufferBudget массивов; его фиксированная
стоимость входит в RSS процесса и измеряется отдельно. Отчёт о тестах содержит
`unsafe.Sizeof` только в тесте и `AllocsPerRun` для горячего пути, без unsafe в реализации.

## 5. Что эта реализация НЕ гарантирует

Текущие ACK подтверждают логические диапазоны, **не номера физических передач**.
Следовательно, нет точного учёта всех отдельных копий датаграмм в полёте; нельзя назвать
эту реализацию RFC 9002/QUIC/NewReno-совместимой. Используются общие идеи ограниченного
окна, уменьшения при потерях, appropriate-byte counting и pacing, но семантика иная.

Избирательное удаление пакетов DPI и перегрузка сети могут давать одинаковый сигнал.
Контроллер консервативно уменьшает скорость и при искусственном удалении. Это не
криптографическая уязвимость, но противник может ухудшать throughput. Чтобы не повторять
постоянно нерабочую упаковку новых DATA, ещё нужна адаптация размеров на основе статистики.

Нет ECN, fast retransmit, полноценной оценки пропускной способности, группировки разных
сессий по общему bottleneck, доказанной TCP-fairness или peer bandwidth negotiation.
Глобальные ресурсные лимиты сохранены, однако они не доказывают сетевую fairness.
ACK/credit трафик не включён в pacer. На длительных высокоскоростных маршрутах окно
16 КиБ сервера может ограничивать throughput независимо от наличия памяти.

Не добавлены streaming API, надёжное завершающее закрытие, Xray bridge, другие carriers,
4–8 КиБ физические датаграммы или новый handshake. Fixed HELLO/ACK длины, экспериментальная
криптография и устаревший compiler остаются известными блокирующими ограничениями.

## 6. Эмуляция узкого канала

Добавлен независимый `emulator.Link`: FIFO-сериализатор с заданными байтами в секунду
и ограниченной очередью; при переполнении выполняется tail drop. Сам Link хранит только
числовое состояние, не payload. Эмулятор событий по-прежнему имеет общий лимит событий
и удерживаемых байтов. Каналы двух направлений независимы.

Поля `Config.RateBytesPerSecond` и `Config.BottleneckBytes` включают Link вместе;
нулевые значения оставляют прежнее поведение. Считаются байты UDP payload, без IP/L2.
Ожидание сериализации занимает очередь; задержка распространения после сериализации
очередь Link не занимает, но соответствующие данные входят в общий бюджет эмулятора.
Дробные времена считаются в наносекундах и округляются вверх только для выдачи события
через существующий миллисекундный scheduler. Отдельный счётчик `LinkDrops` отделён от
`QueueDrops` памяти самого эмулятора.

Это модель, не Linux qdisc и не имитация TSPU. Seed воспроизводит PRNG, но реальные UDP
потоки/планирование ОС не детерминированы полностью. Сравнение использует настоящий
отдельный UDP-релей и точное сопоставление каждого сообщения.

## 7. Проверки и критерии

Регрессии проверяют: ограничение начального burst и cwnd; увеличение только по новым
ACK; отказ на ACK неотправленных байтов; единственность реакции на старый полёт;
повторы при заполненном окне; приоритет управляющего обмена; idle restart;
отсутствие аллокаций pacer; полную доставку с переупаковкой; сериализацию и пределы Link;
асимметричный узкий канал, реальные потери, поддельные пакеты и совместимость.

Измерения и фактические результаты (включая ухудшения) публикуются в BUILD-REPORT.md.
Ни один успешный короткий loopback-тест не является подтверждением работы в Windows,
на узле с 2 ГБ, совместно с Xray, в сети провайдера или под многодневной нагрузкой.
