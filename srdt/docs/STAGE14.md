# Stage 14 — многоклиентский UDP-сервер и сквозной бюджет буферов

Дата: 2026-11-01. Основа: полный архив Stage 13.

## Объём этапа

Реализован работающий многоклиентский **echo**-сервер, совместимый с существующим
защищённым форматом и кадрами reliable. Это ещё не TCP bridge к Xray и не новая
криптографическая спецификация. Исходные режимы CLI не удалены.

## Изменения архитектуры

`netreliable.Server` владеет одним UDP-сокетом. Диспетчеризация идёт по SessionID и
закреплённому адрес:порт клиента. Один цикл последовательно изменяет состояния сессий.
`Stats()` защищён отдельной общей блокировкой для безопасных снимков; блокировок на
каждую сессию нет. Ожидание сокета не удерживает эту блокировку.

В min-heap лежит не более одной записи на живую сессию. Запись планирует отправку,
повторную попытку либо истечение сессии. Простаивающие сессии не сканируются на каждом
входящем пакете. Число таймерных событий и отправок за один проход ограничено, чтобы
не вытеснять обработку входящих данных. Это ограничение работы, **не congestion control**.

Входящие буферы и очередь ответа создаются только после аутентифицированного сообщения.
На HELLO проверяются лимит сессий, лимит по IP, реестр использованных ID и общий token bucket.
Неаутентифицированный трафик не создаёт карту адресов произвольного размера.

## Владение памятью

`reliable.Budget` теперь считает длину payload и размер bitmap: `N + 8*ceil(N/64)`.
Он разделяется входящими сборщиками и исходящими очередями всех сессий нового сервера.
Служебные map, sentRange, AES-GCM, аллокатор, runtime и сокетные буферы в этот счётчик
**не входят**. Поэтому дополнительно ограничены число сессий, сообщений и история ID,
а RSS измеряется отдельно.

`AcceptRetained()` возвращает `Received` с действующим резервом бюджета.
`Queue.EnqueueReceived()` переносит payload и bitmap без копирования. Bitmap очищается
и используется уже как карта ACK отправителя. После передачи владения вызывающий код
не должен сохранять или изменять массивы. `Release()` необходим при отказе от сообщения.
Оба объекта требуют внешней сериализации; новый сервер обеспечивает её общим циклом.

RX и TX делят единый лимит payload и количества сообщений на сессию. Место для ответа
тем самым не исчезает между получением последнего фрагмента и постановкой ответа в очередь.
ACK завершающего фрагмента отправляется после успешной передачи владения в очередь ответа.
При недостатке ресурсов новый фрагмент не подтверждается, состояние под него не выделяется.

Закрытие/таймаут освобождают входящие и исходящие резервы. Удалённые элементы очередей и
heap обнуляются, чтобы backing array не удерживал уже завершённые объекты с буферами.

## Найденная взаимная блокировка окон

Первый процессный тест 200 клиентов × 32 сообщения × 16 КиБ не доставил сообщения за
120 секунд. Старый Batch-клиент одновременно запускал все сообщения. Получатель мог
занять весь лимит активных сообщений, а окно отправителя — заполниться данными остальных,
не принятых сообщений. Для завершения уже принятых сообщений требовалось отправить новые
байты, но окно было полностью занято. Одни повторные передачи это не исправляли.

Исправление: `ExchangeBatch()` ставит в очередь группы до 4 сообщений и до 64 КиБ суммарно.
Следующая группа начинается после получения всех ответов и подтверждений предыдущей.
Одиночное сообщение, превышающее этот размер, идёт отдельно (и должно быть разрешено
конфигурацией получателя). Группа помещается в окно отправителя, поэтому все её исходные
фрагменты могут быть отправлены независимо от ACK соседних сообщений.

Это консервативная политика текущего лабораторного клиента, а **не согласованный по сети
receive-window/credit protocol**. Она ограничивает число одновременно активных сообщений,
но не требует создавать новую криптографическую сессию. Добавлен регрессионный тест
`TestMultiBatchLargerThanReceiverWindow`. Неудачная попытка сохранена в
`stage14-before-window-fix-*`; итоговые проверки относятся к исправленному коду.

## Повторные передачи и CPU

`Queue.NextSized()` различает размер новых и повторно отправляемых фрагментов.
Новые данные продолжают использовать основной размер; только повторы получают меньший.
Смена больше не привязана к возрасту всей сессии. Это фиксированные два размера,
не статистический адаптивный алгоритм и не случайное распределение пакетов.

При повторе допускается включить ранее подтверждённые байты внутри короткого диапазона.
Это не меняет содержимое сообщения, но не позволяет разреженным однобайтовым ACK
раздробить каждую исходную запись на сотни отдельных записей. Проверка добавлена в
`TestSparseACKsDoNotExplodeRetryMetadata`. Побайтовые bitmap остаются; полный range-SACK
и пересмотр CPU-стоимости больших сообщений — будущая работа.

Декодер reliable больше не вызывает Encode для проверки и не выделяет копию кадра.
`TestDecodeDoesNotAllocate` проверяет отсутствие выделений на корректном входе.

## Повторы HELLO и логических сообщений

Повтор того же HELLO от того же адреса возвращает сохранённый WELCOME, с ограничением
частоты. Сессия, счётчики и таймаут жизни не сбрасываются. Использованные SessionID
сохраняются после удаления сессии в ограниченном реестре. При заполнении реестра новые
подключения отклоняются: старые записи под прежним ключом не вытесняются.

Это защита в пределах жизни одного нового Server. Конструктор и приложение должны
использовать новую Identity при новом жизненном цикле; долговременное хранение идентичности
и безопасная ротация ключей ещё не реализованы. Старые single-peer harness остаются отдельно.

Echo-запросы имеют последовательные нечётные ID; ответы — ID+1. Отслеживается непрерывная
граница завершённых запросов и не более 128 ID впереди неё. Старый ID после вытеснения из
кеша уже не создаёт новое сообщение. Слишком старый повтор без сохранённой длины игнорируется;
безгранично поздняя доставка и восстановление после перезапуска не обещаются.

## Проверки и пределы интерпретации

Полные команды: `scripts/verify.sh`. Реальные процессы: `scripts/integration.py --bulk`.
Итоговые числа: [BUILD-REPORT](BUILD-REPORT.md), исходные JSON и журналы рядом.

В отчёте отдельно показаны 1000 подключённых, но простаивающих клиентов; 32 активных с
фильтрацией размеров; 200 активных с 100 МиБ суммарно; 100 МиБ через одну сессию.
Каждый ответ сравнивается побайтово. Генератор работает отдельным процессом, использует
детерминированные тестовые данные; криптографическая случайность независима от seed.

Во всех случаях измеряется Linux loopback, не реальный WAN. `GOMAXPROCS=2` не имитирует
слабый процессор. GOMEMLIMIT — мягкий ориентир runtime. Windows только кросс-компилирован.
Внешний UDP-эмулятор, реальные IP-фрагменты и работа против DPI не проверялись. Размер
внешней датаграммы криптографического прототипа пока ограничен 1200 байт.

## Следующие приоритеты

1. Согласованные приёмные кредиты/окна между сторонами, чтобы заменить отбрасывание
   новых сообщений при нехватке места управляемой остановкой отправителя.
2. Адаптивный RTO, pacing и congestion control; измерять полезные байты на CPU-секунду,
   а не только целостность доставки. Текущая большая нагрузка вызывает много лишних повторов.
3. Полноценный клиентский API длительной сессии с ограниченным внешним Send/Receive,
   затем TCP bridge к проверенной конфигурации sing-box/Gate/Xray.
4. Проверенный механизм криптографического установления сессий, индивидуальные полномочия,
   ключевые эпохи и безопасная ротация; только после этого публичные эксперименты.
