# Stage 17 — скользящее окно резервирования, адаптивный RTO

Основа: полный архив Stage 16. Прототип для лаборатории; не готов к публичному сервису.

## Задача и границы этапа

Stage 16 устранил передачу DATA без памяти у получателя, но отдельный OPEN/GRANT
для каждого сообщения в обе стороны добавил задержку. Stage 17 сохраняет строгое
резервирование, отделяя объявление будущей потребности от очереди фактических данных.
Дополнительно устранены преждевременные повторы при RTT, близком к старому RTO 80 мс.

Это по-прежнему **message-based UDP echo harness**. Потоковое API, Xray bridge,
TCP/WS/HTTP2/QUIC carriers, индивидуальная авторизация и эксплуатационная криптография
не добавлены. Весь пакет UDP всё ещё ограничен 1200 байт; сообщения фрагментируются
в SRDT, а экспериментов с IP-фрагментацией 4–8 КиБ в этом этапе нет.

## 1. Согласование ёмкости окна

Новые внутренние типы:

| Тип | Значение | Поля |
|---|---:|---|
| WINDOW_OPEN | 7 | ID = верхняя запрашиваемая граница; Total = ёмкость одного сообщения |
| WINDOW_GRANT | 8 | ID = верхняя реально зарезервированная граница; Total = та же ёмкость |

Offset обязан быть нулём. Ёмкость неизменна в пределах направления сессии.
Для echo запросы имеют ID 1,3,5…, ответы — 2,4,6…; библиотечный SendWindow
получает начальный ID и шаг отдельно и не знает о смысле содержимого.

Граница является накопительной: GRANT(7, 4096) означает, что соответствующие
ID 1,3,5,7 были зарезервированы, а не что отправитель получил четыре дополнительных
разрешения поверх ранее выданных. Более старый/повторный GRANT не увеличивает окно.
Разрешение вне реально отправленной заявки, с другой ёмкостью или другим доменом
ID отклоняется. Переключение на старые правила внутри сессии запрещено.

Ключевой инвариант:

> Перед публикацией каждого нового ID получатель резервирует BufferCharge(capacity).
> DATA само по себе никогда не создаёт разрешение. Освобождённая память может быть
> предоставлена только НОВОМУ ID, а не повторному использованию прежнего.

Кумулятивная граница допускает компактное состояние отправителя. Получатель хранит
индивидуальные ограниченные резервы только для ещё не завершённых сообщений.
Максимальное число обещаний ограничено совокупными RX+TX лимитами сессии и общим
бюджетом, независимо от того, сколько будущих ID запрашивает приложение.

### Уточнение длины

ReserveCapacity резервирует максимум, не создавая массив payload. Первый корректный
DATA фиксирует фактическую длину <= capacity. Излишек резерва освобождается;
последующие фрагменты обязаны содержать уже установленную длину. Неверный первый
фрагмент не уменьшает резерв. При сборке и передаче Received в очередь ответа
сохраняется тот же учёт реальных буферов; дополнительной копии payload нет.

ReserveCapacity нельзя вызывать для повторной выдачи старого кумулятивного GRANT.
Потерянный GRANT восстанавливается отправкой текущей границы без нового резервирования.
Неиспользованные разрешения не отзываются на работающей сессии: задержанный пакет
не должен получить разрешение на память, уже отданную кому-то ещё. Закрытие/таймаут
всей сессии освобождает и неиспользованные резервы.

### Планирование и справедливость

Используется прежний общий список ожидающих сессий. За один проход выдаётся не более
одного слота на сессию и обрабатывается ограниченное число сессий. Неудачный полный
проход засыпает до освобождения ресурсов или новой заявки. К старым точным OPEN
применяется тот же планировщик: новые окна не получают отдельной приоритетной очереди.

Повторные заявки не продлевают deadline отсутствия прогресса. Разрешения на будущие
ответы, не открывающие передачу реально ожидающего payload, также не считаются
прогрессом. Запоздалый REJECT уже разрешённого ID игнорируется. Заявка, выдача слота,
передача DATA и получение ACK различаются; переполнение буферов не трактуется как
повод повторять весь payload.

## 2. Конвейер в тестовом клиенте

ExchangeBatch сохраняет до четырёх активных транзакций и до 64 КиБ их payload
(либо одно большее сообщение в допустимом legacy single-message harness).
Заявки могут опережать очередь на четыре сообщения. Это только граница спроса,
не дополнительная копия данных или обещание памяти со стороны отправителя.

Для echo приложение заранее знает максимальную длину и будущие ID ответов:
сервер объявляет эту обратную потребность, не дожидаясь полной сборки первого запроса.
**Это оптимизация предсказуемого echo workload**, а не универсальная возможность
предсказать произвольный ответ Xray. Общая очередь поддерживает предварительное
объявление потребности; приложение с неизвестным будущим ответом может сделать это
позже и понести начальную задержку согласования.

Ёмкость сейчас выбирается по максимальной длине входной пачки. Неоднородная пачка
может временно резервировать больше памяти, чем фактически использует. Общие лимиты
не нарушаются, но число доступных слотов уменьшается. Менять capacity в живом окне
нельзя; нужны новая сессия либо будущий версионированный механизм изменения окна.

Клиент также соблюдает предел отставания в 128 ID относительно старейшей незавершённой
транзакции: один медленный пакет не должен привести к запросу недопустимо далёких ID.
Это сознательное ограничение, а не неограниченное независимое завершение сообщений.

## 3. RTO

На направление сессии используется один RTTEstimator. Он вычисляет SRTT/RTTVAR,
а не хранит таймер на пакет. Начальный RTO — 300 мс, нижняя граница — 40 мс,
верхняя — 3 с. Измерения берутся только из полностью подтверждённых исходных диапазонов,
которые ни разу не повторялись. Повторный/некорректный ACK не является новым измерением.

Выборка ограничена примерно одним независимым наблюдением на RTT: сотни близких ACK
одного burst не должны искусственно свести оценку разброса к нулю. При таймаутах
пауза конкретного диапазона экспоненциально увеличивается, до верхнего предела.
Перепаковка одного повтора на более мелкие части не создаёт новые дескрипторы.

Использованы идеи RFC 6298 (SRTT, RTTVAR, исключение неоднозначных измерений), но
**это не реализация TCP/RFC 6298**: минимальный таймаут иной. Механизм также НЕ является
congestion control, pacing или QUIC recovery. Ограниченное число неподтверждённых
байтов не заменяет эти функции.

## 4. Изменяемый размер новых управляющих сообщений

WINDOW_OPEN и WINDOW_GRANT упаковываются во внутренний envelope:

    0x80 | uint16 inner_length | reliable_frame | padding

Внутри AEAD всё аутентифицируется; padding нулевой до шифрования. Длина padding
выбирается независимо через crypto/rand: 16..255 байт. Итоговая UDP payload новых
управляющих сообщений — 77..316 байт. Повтор заявки имеет новый nonce и другую
упаковку. Парсер ограничивает длины и запрещает вложенные envelope.

Это убирает фиксированную длину 58 байт именно у новых WINDOW-сообщений.
Это **не маскировка под HTTP/QUIC**, не доказанная устойчивость к ТСПУ и не изменение
всего wire format. Старые OPEN/GRANT остаются 58 байт, ACK — 62 байта,
HELLO — 81 байт. Реальный тест выявил, что фильтр 77..180 блокирует сам HELLO;
для него сохранён ожидаемый отказ без сессии и резервов. Начальный экспериментальный
handshake требует отдельной переработки, не косметического добавления байтов вне MAC.

### Ошибки локальной UDP-записи

Временный timeout/ошибка отдельной датаграммы не является ACK и не освобождает
данные. Отправитель сохраняет их в очереди для повторной упаковки. Невосстановимые
локальные ошибки по-прежнему возвращаются вызывающему коду. Аналогично исправлен
тестовый UDP-релей: единичный write timeout теперь считается дополнительной потерей
с отдельным счётчиком, а не выключает весь эмулируемый канал. Удаление этого
артефакта стенда не ослабляет проверку полноты доставки.

## 5. Совместимость

* Stage 17 клиент по умолчанию использует оконный режим.
* Stage 17 сервер принимает и Stage 16 точное согласование, и новые окна.
* Новый клиент со старым Stage 16 сервером требует явного --legacy-credits.
* Автоматического downgrade нет; старый сервер с новым режимом завершится по timeout.
* --allow-legacy-data относится к ещё более старому DATA-first режиму и сохранён.
* Существующие CLI-флаги не удалены. Новые типы предназначены для лабораторной версии;
  полноценное версионированное согласование возможностей остаётся незавершённым.

## 6. Ресурсы

Новых goroutine/таймеров на сессию, сообщение или диапазон не создаётся. Сохраняется
один серверный цикл событий и общая heap-очередь таймеров. Добавлены постоянные
по размеру поля окна и оценки RTT; массивы по максимальному размеру окна не создаются.

Общий бюджет — 64 МиБ учитываемых payload/bitmap/метаданных повторов; 64 КиБ суммарного
RX+TX payload и восемь сообщений на сессию. Резервирование capacity подчиняется тем же
лимитам. Runtime, maps, allocator overhead, криптографическое состояние и сокеты не
входят в BufferBudget, поэтому отдельно измеряется RSS серверного процесса.

## 7. Тесты и оставшаяся работа

Новые тесты покрывают повтор/перестановку разрешений, ложное увеличение кредита,
обязательное резервирование до DATA, разную длину сообщений, потерю управления,
общий бюджет на одно сообщение, справедливость с legacy-очередью, освобождение
неиспользованных резервов, ограничения lookahead, RTO/Karn/backoff и envelope bounds.
Фактические результаты всех запусков — в BUILD-REPORT.md и stage17-* журналах.

Обязательные следующие направления: congestion control и pacing, заменяемый
проверенный handshake/эпохи/индивидуальные ключи, конечный ACK/close вместо 300-мс
linger клиента, потоковое API без готовой пачки, тесты Windows/Ubuntu/WAN и слабой VPS,
интеграция с Xray/sing-box. 100 МиБ loopback и короткий fuzz не означают готовность
к эксплуатации или устойчивость против реального DPI.
