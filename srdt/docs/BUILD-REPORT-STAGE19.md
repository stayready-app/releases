# Stage 19 — отчёт о сборке, корректности и ресурсах

Дата: 2026-11-01. Исходный архив Stage 18 проверен по всем 725 записям его манифеста;
ошибок нет. SHA-256 и источник записаны в `stage19-provenance.json`.

## Условия

Go 1.23.2, Linux amd64. Сервер и нагрузочный генератор — отдельные процессы.
Для сервера: GOMAXPROCS=2 и GOMEMLIMIT=128MiB. Измеряются только серверные
`/proc/<pid>/status` и CPU ticks; период опроса 20 мс. RSS — наблюдавшийся максимум,
а не гарантированное обнаружение каждого краткого пика. GOMEMLIMIT мягкий, не
жёсткое ограничение RSS; GOMAXPROCS не имитирует слабый физический CPU.

Все сетевые тесты — loopback, частично с реальным промежуточным UDP-релеем и
искусственными нарушениями. На Windows бинарники не выполнялись; на удалённой
слабой ноде 2 ГБ с Xray не запускались. Результаты не являются измерением VPN.

## Проверки

* `scripts/verify.sh`: build, полный test, полный race, vet, три повтора сетевых
  регрессий, три коротких fuzz-теста, восемь Linux/Windows amd64 сборок — PASS.
* После последней правки Close отдельно повторены **полный** `go test -count=1 ./...`
  и **полный** `go test -race -count=1 ./...` — PASS; `stage19-final-tests.txt`,
  `stage19-final-race.txt`. Бинарники построены после этой правки.
* Новые тесты покрывают формат, неправильные/повторные/запоздалые receipts,
  независимый полёт двух копий, RTT повтора, кольцо, бюджет, Close и 1000 журналов.
* Новый fuzz: недопустимый ACK не изменяет логический/пакетный полёт и владение
  данными. См. `FuzzPacketReceipt` и журнал `stage19-verification.txt`.
* 1000 журналов зарезервировали ровно 8 192 000 байт, после удаления сессий резерв
  вернулся к нулю. Дополнительных per-packet/per-session goroutine нет.
* Перенос регрессионного теста Close на неизменённый Stage 18 воспроизвёл ошибку:
  закрытая очередь всё ещё генерировала WINDOW_OPEN. Новая версия отклоняет это.
  Журналы: `stage19-close-regression-before.txt`, `stage19-close-regression-after.txt`.

`stage19-pre-hardening-verification.txt` — намеренно прерванная промежуточная
проверка, не доказательство успешной итоговой сборки. Основной журнал —
`stage19-verification.txt`; итоговые статусы — `stage19-measurement-status.txt`.

## Парное сравнение 200 клиентов

Обе версии заново собраны одним compiler. Три чередующихся запуска каждой:
200 клиентов × 32 сообщения × 16 КиБ = 100 МиБ в одну сторону плюс эхо.
Каждый ответ проверен побайтово. Нагрузочные сценарии выполнялись последовательно.

| Медиана трёх запусков | Stage 18 | Stage 19 |
|---|---:|---:|
| Успешные запуски | 3/3 | 3/3 |
| Время всей нагрузки | 4.373 с | 4.137 с |
| CPU сервера | 3.56 с | 3.98 с |
| Максимум RSS, медиана | 33.04 МиБ | 37.77 МиБ |
| ResourceDrops | 0 / 0 / 0 | 0 / 0 / 0 |

Время уменьшилось примерно на 5.4%,
но CPU вырос примерно на 11.8%,
а медиана максимумов RSS — на 4.73 МиБ.
Это **не универсальный выигрыш производительности**. Три запуска — короткая серия,
не статистическое доказательство. В новой серии также больше повторных DATA;
нельзя приписывать весь рост CPU только стоимости поиска в журнале.

Подробные исходные данные: `stage19-comparison/summary.json` и журналы каждого
запуска в этой папке. Неудачных процессных запусков кандидата в этой серии нет.

## Процессные испытания текущей версии

| Сценарий | Результат | Время | Максимум RSS сервера | Пик резерва журналов |
|---|---|---:|---:|---:|
| baseline | PASS | 0.642 с | 6.92 МиБ | 0.250 МиБ |
| filter | PASS | 2.223 с | 7.64 МиБ | 0.250 МиБ |
| idle | PASS | 1.481 с | 18.12 МиБ | 7.812 МиБ |
| long-batch | PASS | 3.678 с | 9.55 МиБ | 0.008 МиБ |
| pressure | PASS | 0.975 с | 9.50 МиБ | 1.000 МиБ |
| active1000 | PASS | 6.328 с | 98.57 МиБ | 7.812 МиБ |

`idle`: 1000 клиентов с маленьким проверочным обменом в новом пакетном режиме,
после чего короткий простой. Журналы сохраняются; это не HELLO-only измерение.
`active1000`: 1000 × 4 × 16 КиБ = 62,5 МиБ плюс эхо.
`long-batch`: 100 МиБ плюс эхо через одну сессию, 6400 сообщений.
`pressure`: 128 клиентов, 8 МиБ плюс эхо при payload-бюджете 8192 байта; отдельно
потребляется до 1 МиБ журналов. Не следует называть 8192 байта памятью всего сервера.
`filter`: удаляются DATA-длины 800–1100 байт в обоих направлениях.

Во всех сценариях выполнены точная проверка данных, отсутствие ResourceDrops,
возврат обоих бюджетов к нулю после остановки, соблюдение 128 записей в направлении.
Учитываемый peak payload budget для active1000: 63.980 МиБ
при лимите 64 МиБ. Это не сумма с отдельным packet-state budget и не RSS.

## Искусственный RTT

Один клиент, 32 × 4096 байт плюс эхо, задержка 40 мс в каждом направлении.
Медиана Stage 18: **1,361 с**, Stage 19: **1,421 с** (около 4,4% медленнее).
Все шесть запусков завершились с точной проверкой. Измеряется весь обмен, включая
инициализацию и существующее завершающее ожидание; не только payload goodput.
Логи: `stage19-comparison/stage18-wan.txt`, `stage19-comparison/stage19-wan.txt`.

## Совместимость

CLI-проверки: новый ↔ новый; фильтрация размеров; старый клиент → новый сервер;
новый клиент с `--legacy-packets` → старый сервер; отказ без неявного downgrade;
явные старые точные разрешения `--legacy-credits`. Все ожидания выполнены.
`stage19-cli-smoke.json`, `stage19-cli-*.log`.

## Среда и ограничения

Новый toolchain получить не удалось: DNS из контейнера недоступен и отдельная
попытка загрузки через download тоже завершилась ошибкой. `govulncheck` не выполнен.
Для эксплуатации требуются пересборка актуальной поддерживаемой версией Go,
проверка зависимостей/библиотеки и самостоятельный аудит схемы ключей.

Новый механизм не завершает congestion control: пока timeout-only loss detection,
без PTO/fast loss/ECN/fairness. ACK не агрегируются и сохраняют фиксированную длину.
Криптография, ключевые эпохи, streaming API, надёжный CLOSE, bridge к Xray/sing-box,
другие carriers, IP-фрагментация 4–8 КиБ и испытания реального DPI не реализованы.
Следующий приоритет — уменьшить цену точного учёта и лишние повторы, не ослабляя
лимиты памяти и доказуемое соответствие receipt конкретной передаче.

## Канал с ограниченной полосой и очередью

Дополнительное парное испытание Stage 18/19: 250 000 байт/с в каждом направлении,
очередь 6000 байт, задержка 20 мс в каждом направлении, 256 КиБ данных плюс эхо.
Три последовательных повтора controlled и лабораторного uncontrolled варианта
для каждой версии. Все сообщения проверены; все сценарии завершились.

| Медиана трёх запусков | Stage 18, controlled | Stage 19, controlled |
|---|---:|---:|
| Время | 3.016 с | 3.208 с |
| Отброшено датаграмм в обе стороны | 7 | 7 |

У Stage 19 при отключённом congestion controller (только лабораторный вариант)
медиана времени 2.386 с и 83 отбрасываний.
Новый точный учёт не дал ускорения на этом узком канале: потери/повторы и политика
таймаутов требуют дальнейшей настройки. Нельзя компенсировать это отключением
ограничений и называть протокол готовым. Короткие серии не доказывают TCP-fairness.

Исходные логи: `stage19-bottleneck-stage18.txt`, `stage19-bottleneck-stage19.txt`;
структурированный итог — `stage19-bottleneck-summary.json`.

## Финальная проверка поставки

После фиксации исходников повторно проверены gofmt/vet и запуск Linux `srdt-test`:
1000 из 1000 сообщений проверены, без потерь. Это отдельный smoke-test генератора
и эмулятора, не замена сетевым reliable-тестам. См. `stage19-final-sanity.txt`,
`stage19-test-cli-smoke.json`. Точные исходники и сборочные скрипты зафиксированы
в `stage19-verified-source-sha256.json`.

Полный ZIP сопровождается `MANIFEST.sha256` для всех файлов, кроме самого манифеста.
Итоговый контроль CRC и соответствия всех файлов манифесту производится после
создания архива; внешний отчёт поставки содержит также SHA-256 всего ZIP.
