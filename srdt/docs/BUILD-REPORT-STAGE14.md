## Отдельные реальные процессы, UDP loopback

Итоговый запуск: `python3 scripts/integration.py --bulk`.
Исходные результаты: [stage14-process-tests.json](stage14-process-tests.json).
Генератор данных и сервер — разные процессы. RSS и CPU берутся **только у сервера**.

| Сценарий | Итог | Время нагрузки, с | Наблюдавшийся max RSS сервера, МиБ | Max учтённых массивов, КиБ | CPU сервера, с |
|---|---|---:|---:|---:|---:|
| 32 клиента, без заданных нарушений | PASS | 0.886 | 8.91 | 589.5 | 0.08 |
| 32 клиента, фильтр 800–1100 байт в обе стороны | PASS | 1.052 | 9.14 | 729.0 | 0.12 |
| 1000 соединений после проверочного обмена, затем простой | PASS | 1.329 | 9.46 | 0.0 | 0.14 |
| 200 клиентов, 100 МиБ суммарно + эхо | PASS | 8.165 | 37.69 | 14076.0 | 8.19 |
| 1 сессия, 100 МиБ + эхо (6400 × 16 КиБ) | PASS | 2.698 | 9.76 | 72.0 | 2.24 |

Во всех тестах проверено точное совпадение каждого сообщения. 100 МиБ означает
104857600 байт исходных сообщений и столько же данных эха в обратную сторону.
Это не измерение одностороннего канала без обратного трафика.
При завершении каждого сервера `active_sessions=0`, `buffer_bytes=0`.

Сервер запускался с `GOMAXPROCS=2`, `GOMEMLIMIT=128MiB`. RSS снимался каждые 20 мс;
это наблюдавшийся максимум, а не гарантированная верхняя граница. Go memory limit
мягкий и не равен RSS. Два Go execution slot не имитируют слабый физический процессор;
весь сервер с Xray/агентами на реальной машине 2 ГБ не испытывался.

Проверка `TestMultiThousandIdleState` дополнительно измеряет retained heap после GC
для 1000 только что созданных сессий менеджера и отсутствие прироста goroutine.
Она проверяет структуру менеджера, а процессный idle-тест выше — реальные соединения.

## Обнаруженная ошибка и производительность

Первый большой запуск завершился таймаутом (0 из 200 клиентов). Выяснилась взаимная
блокировка отправляющего окна и ограничения активных сообщений получателя.
Сохранён журнал [неудачного запуска](stage14-before-window-fix-process-tests.json).
После изменения группировки запросов добавлен регрессионный тест; оба итоговых
100-МиБ теста выше прошли. См. STAGE14.md для объяснения исправления.

В итоговом 200-клиентском тесте было 359800 отказов принять новый
фрагмент при занятых ресурсах. Это **не повреждения доставленных сообщений** и не
искусственный сетевой loss, но лишняя нагрузка на CPU/сеть: требуется согласованный
flow control, адаптивный RTO и congestion control. Низкий RSS не означает, что
производительность уже оптимальна.

## Что эти проверки не подтверждают

Нет испытаний реальных DPI/ТСПУ, маршрутов с IP-фрагментацией, внешнего fault-relay,
устойчивости под DDoS, многодневных утечек, интеграции sing-box/Xray и production key exchange.
Сервер нельзя публиковать как готовый сервис. Все полные проверки относятся к этому
снимку исходников; журналы STAGE1–13 являются историческими.
