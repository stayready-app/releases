# Безопасность и ограничения эксплуатации — Stage 16

**Лабораторный прототип. Публичная эксплуатация и реальные пользовательские ключи запрещены
до закрытия перечисленных ниже блокирующих требований.** Исправление найденных ошибок и
успешные тесты не означают криптографического аудита или доказательства корректности.

## Изменения Stage 16

Без разрешения GRANT новый reliable server не принимает DATA неизвестного сообщения.
Повторные OPEN/GRANT не удваивают резерв; задержанный BLOCKED не отзывает разрешение.
Резервы не отзываются по отдельности внутри живой сессии — для аварийного освобождения
закрывается сессия. По умолчанию downgrade к DATA-first запрещён; legacy-режим включается
явно только для лабораторной совместимости. Это защита памяти, не защита от всех DoS.

## Исправленные опасные случаи

* Повторный AcceptHello под тем же объектом Identity больше не создаёт заново ключи/счётчики.
  Активный повтор HELLO возвращает сохранённый WELCOME, не новую шифровку с прежним nonce.
  Это относится и к прежним reliable echo API, теперь использующим общий сервер. Уникальность
  nonce при данном ключе — требование AEAD, а не необязательная оптимизация [1].
* Конфликтующий фрагмент проверяется целиком до изменения сборки. Поддельные пакеты не
  продвигают replay-окно. Неправильный ACK не подтверждает клиента/прогресс сессии.
* Отложенные сообщения не могут заново доставляться после удаления их ID из кеша:
  используется монотонная граница retirement. Это требует оговорённой модели ID.
* Число мелких сообщений, диапазонов повторной передачи и событий эмулятора ограничено.
  Неверные размеры/ключевые аргументы не вызывают воспроизведённые ранее panic.
* Ошибка одной UDP-датаграммы или просроченный таймер не должны останавливать shared server.
  HELLO retry клиента идёт по таймеру, а не в ответ на каждый вставленный пакет.

## Что по-прежнему блокирует production

1. **Криптография.** X25519 + общий лабораторный PSK + AES-256-GCM — экспериментальная
   конструкция, не стандартный проверенный handshake. ChaCha20-Poly1305, индивидуальные
   авторизации/отзыв, key epochs и безопасная ротация не реализованы. Сервер имеет новый
   ключ на каждый запуск, но серверной forward secrecy внутри запуска нет. Одного знания
   public key недостаточно для подделки HELLO без PSK; однако общий PSK не обеспечивает
   индивидуальные полномочия клиентов.
2. **Жизненный цикл ключа.** Identity нельзя копировать, изменять или восстанавливать из
   прежнего private key с пустым реестром. Его собственный реестр ограничен 1 000 000 ID;
   серверный — по умолчанию 65536 ID. При заполнении новые подключения отклоняются.
   Сброс реестра без новой криптографической эпохи небезопасен. Для длительного сервиса
   нужна проверенная схема ротации/перезапуска, а не ручная очистка map.
3. **Нагрузка и доставка.** Реализованы аутентифицированные разрешения на сообщения с
   резервированием памяти и ограниченной очередью ожидания (STAGE16.md). Нет адаптивного
   RTO, congestion control и сетевого pacing. Фиксированные окна/лимиты работы CPU не заменяют управление
   перегрузкой UDP [2]. Успешная доставка в тесте с RTT 80–200 мс не означает эффективной
   работы: лишние повторы при текущем RTO 80 мс остаются.
4. **DoS.** Глобальный hello rate limit и память ограничены, но атакующий способен занимать
   общий admission budget/CPU. Нет полного anti-amplification/path-validation протокола,
   индивидуального rate limit по подтверждённой авторизации и тестирования DDoS на канале.
5. **Память.** Общий Budget считает payload, bitmap и резерв метаданных диапазонов. Это
   не RSS/cgroup cap. Объекты, crypto, runtime, промежуточные аллокации и буферы ядра
   учитываются иначе. GOMEMLIMIT — мягкий предел Go runtime [3].
6. **Семантика ID.** Receiver требует неповторяемые монотонные ID с ограниченным отставанием.
   Старый неизвестный ID отвергается. Durable exactly-once, возобновление после падения,
   миграция NAT/адресов и подтверждение обработки приложением не реализованы.
7. **Среда сборки.** Здесь установлен Go 1.23.2; он вне поддерживаемых веток по политике Go [4].
   Внешние Go-модули отсутствуют, но это не исключает уязвимостей standard library/runtime.
   В Stage 15 попытки обновления toolchain завершались ошибками доступа к сети. Stage 16
   также собран имеющимся Go 1.23.2; успешного обновления в этом этапе не было. Актуальный govulncheck
   не запускался. Поставляемые бинарники предназначены только для лаборатории.
   Перед релизом обязательны поддерживаемый Go с security fixes, повторная сборка/тесты и
   vulnerability scan. Нельзя считать `go vet` или race detector заменой security scan.
8. **Маскировка.** Видимые заголовки/длины/HELLO-поведение остаются. Новые OPEN/GRANT/BLOCKED/
   REJECT имеют постоянный внешний размер 58 байт. При постоянной фильтрации этой длины
   новый обмен прекращается по timeout: padding/fallback контролей ещё не реализованы. Никаких подтверждённых
   гарантий устойчивости к DPI/ТСПУ нет. Максимум датаграммы всё ещё 1200 байт; IP-фрагментация
   и альтернативные носители пока не реализованы.

PSK в CLI виден в списке процессов; используйте только случайные тестовые значения.
Тестовые fixtures с PSK `11...11` или нулевыми байтами намеренно публичны.
Session/Queue/Receiver не допускают конкурентных вызовов без внешнего владельца.
Не удерживайте заимствованные scratch-срезы после следующей операции/ownership transfer.
